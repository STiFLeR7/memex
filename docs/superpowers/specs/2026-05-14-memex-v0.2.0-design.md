# Design Spec: memex v0.2.0

**Date:** 2026-05-14
**Status:** Approved
**Target Version:** v0.2.0

## 1. Overview
memex v0.2.0 evolves the system from a single-repo, local-only developer tool into a production-grade team context engine. This release focuses on three pillars: confidence-weighted write discipline, multi-repo support via a global daemon, and HTTP/SSE transport for remote/team usage.

## 2. Architecture: The Unified Central Hub

The system will move to a "Unified Central Hub" model where a single background process manages multiple repositories and serves multiple agents simultaneously.

### 2.1 The Global Registry
A central registry file will be maintained at `~/.memex/registry.json` (or a platform-appropriate equivalent) to track registered repositories and security credentials.

**Schema (`registry.json`):**
```json
{
  "repos": [
    {
      "path": "D:/memex",
      "name": "memex",
      "active": true
    }
  ],
  "keys": [
    {
      "name": "admin",
      "key": "mx_...",
      "created_at": "2026-05-14T..."
    }
  ]
}
```

### 2.2 The Global Daemon
The `memex watch` command will transition to a global observer:
- Loads all active repos from the registry.
- Spawns an `FSObserver` and `CommitPoller` for each repo within a single `asyncio` event loop.
- Shares a single Neo4j connection pool and configuration.
- Routes all events through a central `EventRouter` that tags every payload with its originating `repo_path`.

## 3. Pillar 1: Confidence-Weighted Write Discipline

To solve the signal/noise problem in agent-recorded decisions, v0.2.0 introduces a bi-temporal confidence model.

### 3.1 Node Schema Updates
`Decision` nodes are extended with temporal and verification metadata:
- `confidence` (float): 0.6 (default for agents), 1.0 (corroborated).
- `source` (string): "agent" | "watcher".
- `corroborated` (boolean): Whether a commit has verified this decision.
- `corroboration_commit` (string): The SHA of the corroborating commit.

### 3.2 Corroboration Logic
The watcher's `CommitHandler` will perform a keyword-based corroboration pass:
1. **Trigger**: A new commit is detected.
2. **Search**: Find pending `Decision` nodes in the same repo created within the last 14 days.
3. **Match**: Compare commit message keywords and touched symbols against the decision text.
4. **Update**: If a match is found, elevate `confidence` to 1.0 and set `corroborated = true`.

### 3.3 Tool Updates
- `get_recent_decisions()` gains a `corroborated_only` boolean parameter.
- Returned decisions include a `status` field (`"corroborated"`, `"pending"`, `"stale"`) derived from the confidence model.

## 4. Pillar 2: Multi-Repo Support

### 4.1 Neo4j Schema
- **New Node**: `(:Repository {path: STRING, name: STRING, added_at: DATETIME})`.
- **Foreign Key**: Every symbol, module, and decision node gains a `repo_path` property.
- **Cross-Repo Edges**: `depends_on` edges are created between modules when the registry can resolve an import to another registered repo.

### 4.2 MCP Integration
All 10 MCP tools will gain an optional `repo` parameter.
- If provided: Tool scopes query/write to that specific repository.
- If omitted: Tool performs a cross-repo search/aggregation.

## 5. Pillar 3: HTTP/SSE Transport & Auth

### 5.1 FastAPI Server
A new transport option `memex serve --transport http` (port 7463) will provide:
- **SSE Endpoint**: `/sse` for standard MCP connectivity.
- **Message Endpoint**: `/messages` for tool execution.
- **Auth**: Bearer token authentication against the `registry.json` named keys.

### 5.2 Key Management CLI
New CLI commands for team leads:
- `memex keys add <name>`: Generate and store a named API key.
- `memex keys list`: View active keys.
- `memex keys revoke <name>`: Invalidate a key.

## 6. Implementation Phases

1. **Phase 6**: Confidence model & Corroboration pass.
2. **Phase 7**: Global registry, Multi-repo schema, and Global Daemon.
3. **Phase 8**: FastAPI HTTP/SSE transport & Key management.
4. **Phase 9**: Integration testing, final audit, and release.

## 7. Success Criteria
- `record_decision()` nodes reach 1.0 confidence on commit corroboration.
- A single `memex watch` instance monitors multiple repos.
- Remote agents can connect via HTTP/SSE using named API keys.
- Audit score: 97+/100.
